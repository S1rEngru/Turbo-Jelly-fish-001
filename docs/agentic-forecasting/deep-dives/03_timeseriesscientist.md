# TimeSeriesScientist：优先参考完整时序分析流程

查阅日期：2026-09-17。简称 TSci；官方仓库采用 MIT 许可证，研究论文为 arXiv:2510.01538，本篇查阅 v2。

## 1、背景

TSci 将预测工作拆为数据整理、计划、预测和报告四种论文角色。其重点是把分析和建模过程一起自动化，而不只是输出未来数值。[论文 v2](https://arxiv.org/html/2510.01538v2)

**入选理由（本项目分析）**：用户目前还在阅读 baseline。这个项目便于理解“训练之外到底有哪些工作可以交给 Agent”，也方便以后把这些工作拆成可检查的模块。

## 2、问题

官方实现把流程列为五个模块：PreprocessAgent、AnalysisAgent、ValidationAgent、ForecastAgent、ReportAgent，使用共享状态连接，并保存报告、图表、预测与日志。[官方 README](https://github.com/Y-Research-SBU/TimeSeriesScientist)

**映射到本项目**：如果新品牌效果不好，原因可能在数据、候选模型或评估流程。只让 Agent 调学习率，会忽略前后环节。分阶段保存证据有助于定位问题。

## 3、难点

论文根据数据分析缩小候选模型范围，再使用验证结果选择配置与集成；集成策略和权重在接触测试集之前确定。[论文 v2，方法部分](https://arxiv.org/html/2510.01538v2)

**本项目分析**：最困难的并非给 Agent 起几个角色名，而是规定各环节什么能改、什么不能改。例如：

- 缺失销量和真实零销量需要分开，否则“清洗”可能改变业务含义。
- 促销尖峰可能是真实信号，自动裁剪异常值可能让模型看起来更平滑却更不实用。
- 季节性诊断不能替代回测；解释合理的模型也可能预测较差。
- 多模块之间应传递结构化证据，不能只传递上一位 Agent 的自然语言结论。

这些零售问题是迁移分析，不是原项目已证明解决的能力。

## 4、实现方法

### 文档确认的模块分工

| 实现模块 | 核心职责 |
|---|---|
| PreprocessAgent | 数据检查、缺失和异常处理 |
| AnalysisAgent | 趋势、季节性等特征分析 |
| ValidationAgent | 候选模型与参数的验证 |
| ForecastAgent | 单模型预测与集成 |
| ReportAgent | 汇总结果和过程说明 |

README 提供 CSV 输入示例和预测长度、切片数量、模型数量等配置，产物包含 JSON 报告及日志。论文四角色与代码五模块是不同抽象层，阅读时不能按名称直接一一对应。[官方 README](https://github.com/Y-Research-SBU/TimeSeriesScientist)

### 如何借鉴（建议）

第一版可以只保留三个阶段：

1. 固定工具生成“数据体检表”，Agent 对结果作解释并提出候选方案。
2. 原 baseline 执行候选实验，固定程序输出分窗口、分品牌指标。
3. Agent 根据实验记录生成结论，明确选择理由和仍待确认的问题。

清洗前后都记录数据摘要与差异，避免结果改变后找不到原因。报告中的每个数字来自实验产物，每个模型选择理由链接到对应运行；没有证据的业务解释应标成假设。

如果采用多 Agent，划分依据应是职责和数据权限，而不是数量。能够用确定性函数完成的检查不一定需要一次 LLM 调用。

## 5、效果

论文覆盖八个基准。表 1 中，ETTh1 的 TSci 为 MAE 2.02、MAPE 23.3；Gemini 对应为 5.20、61.1。另一个值得注意的例子是 ECL：TSci 的 MAE 667 优于 Claude 的 844，但 MAPE 40.2 高于 Claude 的 32.2。[论文 v2，表 1](https://arxiv.org/html/2510.01538v2)

这说明在论文设置中存在明显改善，也说明不能把“总体较好”理解为“每项指标都最好”。上述数值是作者报告，未由本项目复现；它们也不是与用户 NeuralForecast baseline 的对照。

对销售场景，后续不宜只照搬 MAPE：零销量和小分母会影响解读。建议保留业务认可的聚合指标，并检查每个品牌、促销期、普通时期以及低销量商品的误差。具体指标口径需要在实际数据与业务目标明确后确定。
