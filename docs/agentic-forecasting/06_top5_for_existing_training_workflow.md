# 基于现有滚动训练逻辑的 Agent 辅助建模 Top 5 深入调研

版本：v1；调研日期：2026-09-17；整理完成：2026-09-18。

本文研究可学习的方法，不实施系统、不要求企业内部数据或完整代码。项目事实附来源编号，完整链接保存在末尾；“迁移分析”是结合用户描述的推导。公开效果均为作者报告，未在本地复现。

## 一、结论和推荐顺序

现有信息足够选择学习对象。核心是围绕现有训练和评估工具，补上由人完成的实验设计、调参、选型与结果判断。财务日历继续由原流程处理，不需要先训练强化学习 Agent。

| 排名 | 项目 | 最值得学习的部分 | 可效仿依据 |
|---|---|---|---|
| 1 | 金融训练 TS-Agent | 训练模板上的受限动作、实验反馈和预算分配 | 公开论文的方法与算法；官方代码未确认 |
| 2 | Microsoft RD-Agent | 假设、实验、执行、反馈、历史记录的分工 | 官方文档与实验循环源码 |
| 3 | Microsoft Finn | 多序列方案管理、更新和重新优化 | 官方 Agent 指南与 API |
| 4 | TimeCopilot | 将 NeuralForecast、诊断和回测封装为工具 | 官方 API 展示的实现代码 |
| 5 | TimeSeriesScientist | 数据特征到候选空间、再到集成的流程 | 论文与开源模块；代码有需要规避的问题 |

**本轮调整：TSci 从第三下调到第五。** 深入查看公开代码发现，其预测失败分支使用测试真实值生成回退预测。方法仍值得学习，但不能直接照搬该代码。其他项目相对顺序不变。这是针对当前需求的学习优先级，不是精度或成熟度排名。

准入标准是开源或充分公开实现方法，满足其一即可。纯闭源且只有宣传的项目排除。TS-Agent 虽没有确认代码，但公开了动作、资源、记忆与搜索算法，符合方法学习要求。MLZero 未进入前五，因为它更侧重从原始数据生成完整 ML 流程，而用户已有训练基础。

## 三、Top 1：金融训练 TS-Agent

### 1、背景

这里指论文 Structured Agentic Workflows for Financial Time-Series Modeling with LLMs and Reflective Feedback，arXiv:2508.13915v1。其场景是已有训练模板、模型代码和领域知识的金融建模。[T1]

### 2、问题

它研究怎样让 Agent 利用已有资产持续修改实验，而不只是写一次训练代码。与用户现有 baseline 相似的是，预测模型和训练执行本身已有基础，缺口在决策和迭代。

### 3、难点

迁移分析：动作太自由会难以判断改动原因；只允许改一两个数又无法扩展模型。需要把模型选择、参数变化、训练策略和运行失败分别记录。案例可以提供候选方向，但不能保证跨品牌有效。

### 4、实现方法

原文将行动分为模型／指标选择、训练改进、超参数配置、执行记录；上下文由静态知识和历史实验组成。先筛候选，再进行少量改进轮次，将更多轮次投给较好方案；loss 降低才替换当前脚本，否则回退。[T1，第 4 节]

这里修正一个容易出现的理解：warm-up 是较少的改进迭代，不等于原文明确定义了统一减少 epoch 的短训练协议。论文以 policy 描述选择行为，也不能仅凭这个词认定它训练了 RL 策略。

迁移到当前流程，最值得效仿的是动作分类与结果保留。比如某模型训练未收敛，可以提出预算或学习率实验；某候选单模型不占优但组合有改善，应保留其组合价值。当前最终输出可能是集成，因此不能只保存一个单模型冠军。

建议将每次尝试表达为：观察到的结果、假设、修改范围、预算、逐 AP 结果、保留或拒绝理由。它可以帮助人决策，不要求立即自主修改整个工程。

### 5、效果

股票实验的 GPT-4o 设置中，MAE 为 4.912，AutoGluon 为 5.258；作者报告五次运行均值。原文将 test metrics 纳入反馈描述，迁移时需另行明确验证和最终留出集边界。[T1，表 1、第 4 节]

这些结果不能证明销售场景提升幅度，也没有单独证明节省企业人工的比例。官方可运行仓库仍未确认。

**优先读**：第 3.2 节资源、第 4 节动作及 Algorithm 1、第 4.2 节轮次分配。保留方法，替换金融模型库与业务目标。

## 四、Top 2：Microsoft RD-Agent

### 1、背景

RD-Agent 将研发过程组织为假设、实现、运行和反馈。官方金融模型场景以 Qlib 为后端，而不是直接针对销售预测。[R1]

### 2、问题

它适合学习怎样让一次建议对应一次真实实验，以及怎样让实验结果进入下一轮。对于人工阅读大量评估结果的现状，这比单纯生成分析报告更接近缺口。

### 3、难点

迁移分析：实验需区分四类失败：假设无法验证、实现没有执行预期改动、对照预算不公平、改进只在局部窗口成立。否则“自动反思”可能只是重新描述结果，没有推动有效搜索。

### 4、实现方法

本轮查看 rd_loop.py，实际职责包括 _propose、_exp_gen、coding、running、feedback、record。历史 trace 参与假设生成，编码器与运行器分开，异常生成不接受的反馈，最后记录实验与反馈关系。代码还提供人在假设与反馈阶段介入的入口。[R2]

迁移分析：已有脚本可被视为实验执行工具。Agent 提出“只修改某模型的窗口范围”或“增加一类候选”，执行层返回真实运行记录；比较层负责相同协议下的评估。对没有变动的模型可研究复用其预测，减少重复训练。

未来新增模型时，Agent 可以给出理由，但是否支持 static/future/history、是否可输出规定 horizon、是否成功执行，应由候选说明和真实运行确认。文字理由不能替代模型接入完成。

与 TS-Agent 相比，RD-Agent 更值得学习实验之间的组织方式；TS-Agent 更值得学习单个训练模板内允许哪些动作。二者可结合，不必整套搬用一个框架。

### 5、效果

官方 Benchmark 页面提供实现能力评测及 RD2Bench 入口，衡量对象不同于跨品牌销量预测。[R3] 本轮所查来源没有可直接用于本项目的销量提升百分比。

通用数据科学示例包含医疗时序分类，不能因为输入有时间维度，就照搬其样本划分做未来 AP 预测。[R4]

**优先读**：R1 六步闭环，R2 各方法的输入输出，R3 的实现能力评测。暂不需要阅读所有量化因子细节。

## 五、Top 3：Microsoft Finn

### 1、背景

Finn 区分首次迭代与新数据更新，保存运行版本、最佳结果及诊断材料。它的价值尤其体现在多序列持续运行。[F1]

### 2、问题

当品牌数量增加，人工成本既来自首次调参，也来自每个 AP 判断哪些方案可以复用、哪些需要重新探索。Finn 提供了后者的具体参考。

### 3、难点

迁移分析：不能每次更新都重新遍历全部搜索空间，也不能永久复用旧方案。不同品牌与层级的退化可能不一致，单个汇总指标不足以决定所有序列一起重搜。

### 4、实现方法

iterate_forecast 提供目标与最大轮数；update_forecast 默认不开启重新优化，允许时按退化条件触发，并有新序列或失败序列回退路径。[F2、F3]

指南还区分供下一步探索的上下文与已保存的较佳预测；全局模型赢家需要保持一致的迭代来源。问答读取预测、配置、EDA 和模型摘要。[F1]

迁移分析：当前应明确两个循环：时间循环推进 AP；搜索循环在固定的历史评估协议内比较模型、参数和组合。复用配置不等于复用权重，也不等于每次更新重新搜索。原脚本如何重训可稍后确认。

另一个值得借鉴的点是：值得继续探索的配置，不一定已经值得替换现有输出。某参数使一个模型改善，却没超过最终组合，可记录为后续方向，而不是立即部署。不要直接照搬 Finn 的 WMAPE 或退化阈值，使用用户现有 eval 后再讨论。

### 5、效果

文档展示了接口和完整更新规则，但未提供隔离 LLM Agent 贡献的严格收益对照。微软历史财务预测收益不能全部归因于该 Agent。

**优先读**：F1 的产物和 production loop，F2/F3 的参数及回退规则。学习状态管理，不要求把 Python 项目迁到 R。

## 六、Top 4：TimeCopilot

### 1、背景

TimeCopilot 将预测与诊断工具提供给 LLM，包含 NeuralForecast 的 AutoNHITS 接口，暴露搜索样本数、后端与配置。[C1、C2]

### 2、问题

它最贴近现有技术栈，可帮助理解如何将训练能力包装成 Agent 可调用且可读结果的工具。但技术栈相似不等于覆盖全部业务逻辑。

### 3、难点

迁移分析：工具返回一个全局分数很方便，却可能丢失品牌、层级、AP 和日周月差异。Agent 只能依据它看得到的证据作判断，接口设计会直接限制决策能力。

### 4、实现方法

本轮核查了 tsfeatures_tool、cross_validation_tool、forecast_tool：模型名与可用预测器核对，回测由预测器执行，再将指标转换为文本。所查片段按 metric 取均值汇总，并不自动保留本项目需要的业务权重。[C1]

输出校验器 validate_best_model 读取 is_better_than_seasonal_naive 字段决定是否重试；该局部片段没有独立重算指标，不能单凭它认定输出已获数值验证。[C1]

迁移分析：最值得参考的是调用契约。原工具可返回数据版本、候选配置、运行状态、预测文件、分 AP 指标和费用；Agent 用这些结果排序下一步行动。static/future/history 的能力兼容应在候选说明中明确，不能依靠模型名称猜测。

组织层级共同出现时，简单平均指标可能与实际业务权重不同，甚至重复反映同一业务量。因此应将它的均值汇总看作示例，最终对齐现有 eval。

### 5、效果

GIFT-Eval 页面对应指定基础模型的中位数集成，报告低于 30 美元计算成本。它不能单独证明 LLM 调参或选型优于固定方法。[C3]

**优先读**：C2 的模型封装，C1 的三个工具与输出校验，C3 的实验对象。无需从所有预测模型内部实现读起。

## 七、Top 5：TimeSeriesScientist，保留方法参考，降低代码信任

### 1、背景

TSci 串联诊断、候选选择、参数验证、集成和报告。论文 Planner 根据分析缩小模型空间，以验证 MAPE 选配置，Forecaster 在测试之前确定集成方案。[S1]

### 2、问题

它覆盖的选模和集成环节，与现有四模型及组合比较最直接相关。但需要核对论文中的方法是否等同于当前代码。

### 3、难点

本轮发现实际实现与论文存在差异，并存在异常路径问题。因此不能仅凭“开源、有论文”就认为每个分支都可靠。这也是它从第三降到第五的原因。

### 4、实现方法与代码核查

validation_agent.py 的主要 run 路径解析候选与参数空间、执行验证再排名；所查优化按 MAE 比较，内部以前 80%／后 20% 切分。文件还有返回随机分数的辅助函数，但主要 run 使用另一条真实模型验证路径，不能据此宣称全部评分随机。[S2]

forecast_agent.py 计算简单均值、加权均值、中位数和截尾均值；有验证 MAE 时主分支使用加权均值，否则使用简单均值。重要问题是模型预测失败时，run 把 test_data 交给回退函数，后者读取测试 value 的均值和标准差生成预测。若该参数是所声明的留出真实数据，这条异常路径会泄漏答案。[S3]

这是静态代码发现，未运行触发；不代表论文实验一定触发，也不能默认当前 main 就是论文实验版本。

迁移分析：学习候选空间生成和集成接口，保留现有 15 种等权组合作为可解释对照。仅有单模型 MAE 不足以刻画逐日误差互补性，LLM 建议的权重仍需真实回测。

失败应记录为失败，或回退到只使用历史信息的合法基线。不能将替代预测作为原模型成功结果，也不能从未来真值构造回退。

### 5、效果

论文有八个基准的作者实验，不同指标并非全部领先。[S1] 本轮代码问题限制了“直接下载即可可靠复现”的判断，但不能反向断定论文结果由该问题造成。

**优先读**：S1 的 Planner/Forecaster，再对照 S2 的 run 和验证函数、S3 的 run 和 ensemble 函数。失败回退代码不可照搬。

## 八、结合当前逻辑，Agent 应研究什么

以下是本次迁移分析，不是五个项目已经共同验证的能力。

### 1. 训练与组合计算分开

四个模型对应 2^4−1=15 个非空组合。已有预测上计算均值，不需要为每个组合重新训练；若现有脚本已如此处理，继续保留。

8 个模型对应 255 个组合，12 个对应 4095 个。这是组合空间增长，不是必须训练同样次数。可以研究缓存各候选在相同起点的日预测，再精确评估组合。Agent 更适合提出新候选、安排实验和解释取舍；只有枚举确实成为成本问题时才研究剪枝。

### 2. 区分训练目标、选型依据和业务接受条件

已知训练用 MAE，最终选型指标尚未确认。月总量准确与每天准确可以不同；某层级改善也可能伴随另一层级退化。Agent 不应自行把所有指标合成未经确认的新分数。

相同超参数便于控制变量，不保证每种架构在各自适合的范围运行。可以研究模型专属参数空间，但应保留训练预算和完整配置，避免将更多计算带来的改善都算作 Agent 能力。

### 3. 区分时间滚动与实验迭代

同一 AP 起点的多个候选应使用相同信息边界。推进到下一 AP 后，新增数据改变了训练条件，不能仅把新旧单一分数之差称为模型改善。这里是在研究比较原则，不要求重新开发现有日期处理。

### 4. 解释分为三种

模型为什么给出某个值、Agent 为什么试某个配置、业务为什么发生变化，需要不同证据。已有归因可以帮助提出消融或特征对照实验，但不直接证明某因素对真实销量的因果效应。具体解释算法待用户补充，不阻塞当前研究。

### 5. 跨品牌经验要带适用条件

有用的记忆应记录数据长度、可用特征、预测长度、评估协议、预算和在哪些窗口成功或失败。新品牌据此排列候选优先级，不应跳过验证。负面结果也要保留，否则会重复花费训练预算。

### 6. 停止与效果评价

预算耗尽、达到业务目标、连续未改善、没有合法候选和执行失败是不同停止原因。返回已确认结果和剩余问题，不自动宣称找到最优模型。

后续评价 Agent 应同时考察人工介入时间、有效实验数量、重复失败率、训练与 LLM 成本、预测表现。保留相同预算的普通调参或固定规则对照，才能分辨 LLM 决策是否有额外价值。训练失败的费用也应计入预算。

核验记录：

- 用论文标题加 GitHub 继续检索 TS-Agent，未确认作者维护的实现；未拿同名项目充数。未找到不代表证明不存在。
- TSci 测试数据回退有代码依据；随机评分辅助函数的存在没有被扩大为主流程全部随机。
- TS-Agent warm-up 按原文解释为改进轮次，避免混同短 epoch 训练。
- TimeCopilot 的基础模型成绩与 Agent 贡献分开；Finn 的接口与企业收益分开。
- 本文是新的场景化报告。旧版保留为历史，后续推荐应优先以本文及其修订为准。
