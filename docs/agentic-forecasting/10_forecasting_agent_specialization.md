# 时序预测训练 Agent 的特化模块：从通用 ReAct 到可信实验闭环

核查日期：2026-09-18。与 [09 通用 Harness 调研](09_open_source_harness_architectures.md)配套。本文优先使用固定版本开源代码，区分仓库现有机制与结合用户场景提出的设计。未运行第三方测试，未执行企业训练。

## 1. 核心判断

通用 Agent 能调用训练工具，不代表已经懂得怎样做合法、可比、有业务价值的时序实验。需要补足的是：
- 任务与特征可见性契约；
- 模型能力注册表；
- 可重复的滚动评估与业务指标；
- 能定位问题的诊断工具；
- 从证据到可检验假设的领域规则；
- 训练作业与实验工件管理；
- 跨版本记忆和可靠终止。

第一版无需训练/微调 LLM，也无需先发明强化学习策略；先通过工具、明确规则、结构化上下文和反馈测试让模型适应任务。只有在评估发现稳定的能力缺口后，才考虑检索增强、示例扩充或模型训练。

目前本轮最值得读的领域实现是 **Microsoft Finn**；TimeCopilot 适合学习专用工具封装，但有不宜照搬的评估边界。RD-Agent 的动作路由仍有价值，详见08文档，但不是本轮唯一来源。

## 2. Finn：本轮最贴近业务流程的实现

仓库：microsoft/finnts。R 实现，不是 NeuralForecast 的即插即用插件。固定版本见来源清单；DESCRIPTION 声明 MIT + file LICENSE，GitHub API 的 NOASSERTION 不应误解为没有开源许可。

### 2.1 领域上下文不是整表塞给 LLM

[R/agent_eda.R](https://github.com/microsoft/finnts/blob/22dd9989da8f390b1da256a6082dde83653202c8/R/agent_eda.R) 读取并整理 ACF/PACF、平稳性、缺失、异常等 EDA 工件。其可迁移点是先通过确定性计算形成诊断，再提供精简摘要。

[R/agent_iterate_forecast.R](https://github.com/microsoft/finnts/blob/22dd9989da8f390b1da256a6082dde83653202c8/R/agent_iterate_forecast.R) 集中实现 reason_inputs、validate_agent_proposal、normalize_agent_run_inputs 和迭代逻辑。上下文包含当前版本结果、旧版参考、最近错误和剩余参数变更额度；建议提交前校验模型、外部回归变量、预测方式及参数兼容性，并规范化配置做重复判断。

这比“你是时序专家，请优化模型”更具体，但其规则对应自身模型和任务，不能不加转换地用于你的 static/future/history。

### 2.2 测试提供了哪些工程证据

[test-agent-duplicate-runs.R](https://github.com/microsoft/finnts/blob/22dd9989da8f390b1da256a6082dde83653202c8/tests/testthat/test-agent-duplicate-runs.R) 检查模型/变量顺序与重复值变化不能逃过语义去重。

[test-agent-global-resume.R](https://github.com/microsoft/finnts/blob/22dd9989da8f390b1da256a6082dde83653202c8/tests/testthat/test-agent-global-resume.R) 包含模拟：全局优化已结束，局部 B 失败；恢复后不再执行全局与已完成 A，只重试 B。本轮读到了调用次数断言，不只是测试名称。

[test-agent-graceful-abort.R](https://github.com/microsoft/finnts/blob/22dd9989da8f390b1da256a6082dde83653202c8/tests/testthat/test-agent-graceful-abort.R) 覆盖建议字段校验、当前版本预算和旧版回放场景；[test-agent-selection-policy.R](https://github.com/microsoft/finnts/blob/22dd9989da8f390b1da256a6082dde83653202c8/tests/testthat/test-agent-selection-policy.R) 覆盖不完整全局结果、不同迭代结果混用等选择边界。本轮未运行，测试存在不等于全部通过。

### 2.3 不能照搬的部分

[R/agent_run.R](https://github.com/microsoft/finnts/blob/22dd9989da8f390b1da256a6082dde83653202c8/R/agent_run.R) 的 execute_node 含可选 LLM 修复分支：解析新工具名/参数后再次动态调用。在此分支内未见独立允许列表校验，不能将它直接视为安全的工具分发范例；实际暴露面还取决于节点配置与运行环境。你的执行器应始终通过固定注册表和参数校验。

Finn 的业务目标、特征规则与 R 后端均不等于你的评估协议；MAPE 类目标也不自动适用于零值、负值或多组织权重。借鉴状态与校验机制，保留现有业务评价定义。

## 3. TimeCopilot：工具和任务结构怎样结合

[timecopilot/agent.py](https://github.com/TimeCopilot/timecopilot/blob/23f56c2c9065a5fed28535f97e3a36486bb26d81/timecopilot/agent.py) 注册时序特征、交叉验证、预测、异常检测工具，并用模型列表校验部分调用；输出有结构化字段。说明领域适配可以主要通过工具和数据依赖完成。

需要注意：validate_best_model 读取模型输出的 is_better_than_seasonal_naive 布尔值；CV 工具聚合指标并更新 self.eval_df。前者不是独立数值比较，后者不能直接替代跨实验档案。你的系统应从实际指标确认胜负，并保留每次评估的独立工件。

[utils/experiment_handler.py](https://github.com/TimeCopilot/timecopilot/blob/23f56c2c9065a5fed28535f97e3a36486bb26d81/timecopilot/utils/experiment_handler.py) 将数据参数和评价接口组织成对象，可参考将 horizon、频率和评估数据作为受控依赖。你的财务 AP 已由现有脚本处理，Agent 应接收已解析协议，不必重新推断日历。

## 4. 用户场景下需要补齐的模块（以下均为设计建议）

已知场景：四个模型、15种等权子集；static/future/history 可配置；扩展窗口、财务AP长度28–35；日预测汇总周/月；解释器；历史参考序列与事实加权修复。七个数据集不自动解释为七个品牌。模型名称与评估细项尚未确认，不影响 harness 调研。

### 模块A：任务契约与特征可见性

只记录字段分组还不够，未来可见性必须以 forecast origin 为参照。

建议元数据：字段含义、角色、生成方式、业务可用时间/滞后、缺失规则、可否进入 decoder、分组和单位。可见性校验由工具完成；Agent 只能选择合法特征。

例如距离月末可预知，未来实际销量不可用；历史月销量当时是否已经关账，也可能影响可见性。level-key 先区分是模型输入还是评价标签，不因位于 static 配置就自动做消融。

读入任务契约还包括财务日历版本、horizon、目标、归一化与逆变换、组织层级、数据/修复版本。日期处理复用已有脚本，不要求用户再解释日期细节。

### 模块B：模型能力注册表

每个候选模型列出：支持哪些外生变量、允许的参数名/类型/范围、horizon和输入长度约束、设备需求、训练/预测入口、checkpoint语义。

Agent 不应假定“所有模型可用同一组超参”；也不应把一次 fit 当作自动断点续训。注册表优先取自实际安装的 NeuralForecast 版本和你的适配器，而不是 LLM 的记忆。

第一版可仅注册当前四个已验证模型。新增模型作为独立的适配任务，不让普通优化循环临时安装任意依赖。

### 模块C：确定性评估服务

eval 返回的不只是一个 value，而是：
- 主业务分数、方向、样本数、协议/指标版本；
- 每个滚动起点、AP、组织层级、预测步长的分项；
- 日/周/月聚合结果、偏差与稳定性；
- 缺失/非有限预测、日期或序列对齐问题；
- 比较基线、实际耗时、是否具备候选资格。

其中硬资格由代码判断；是否接受小幅提升，按预先定义的业务规则。反复用于调参的分数属于开发评估，最终留出时间段不进入常规 Agent 上下文。

修复和标准化只作用在合法训练数据范围。评价使用原始实际目标并按协议逆变换；不能通过修平验证标签“改善成绩”。

### 模块D：从一个分数升级为诊断证据

| 观察 | 应查询的证据 | 可提出的下一项实验 | 不能直接下的结论 |
|---|---|---|---|
| 月末误差大 | 同协议的月末/其他日残差、可见特征覆盖 | 消融或补充一个合法月末特征组 | 必须换 Transformer |
| 训练好、后续AP差 | 学习曲线、训练/验证差距、分AP结果 | 调整正则、容量或输入窗口之一 | 一定过拟合 |
| 少数组织很差 | 规模、稀疏性、层级、缺失分布 | 在固定协议下检验一个分组方案 | 全局模型无效 |
| 远期步长更差 | 按预测步长误差、外生输入可用性 | 检验一个窗口/模型配置 | 历史特征无用 |
| 某列归因低 | 相关性、归因稳定性、成组消融 | 移除一个语义组再验证 | 此列没有因果作用 |
| 某AP异常 | 走步残差、业务事件、修复前后敏感性 | 验证既有repair参数方案 | 异常等于错误数据 |

这里的“归因”应区分预测贡献、错误分布和真正的因果归因。LLM 可以提出原因假设；单次效果变化不能证明因果，也不能把噪声解释成机制。

### 模块E：领域动作及前后条件

工具粒度适合落在“一个可评估实验”，不必是一条底层Python语句。示例接口：

| 工具 | 输入 | 输出/约束 |
|---|---|---|
| inspect_residuals | experiment_id、受控切片维度 | 指标和工件引用；不修改模型 |
| inspect_attributions | experiment_id、特征组 | 归因方法、样本范围、稳定性 |
| validate_proposal | parent_id、配置差异 | 合法性、预计资源、缓存命中、错误码 |
| submit_experiment | 验证后的proposal_id、幂等键 | job_id，不阻塞到训练结束 |
| collect_result | job_id | 完整性、模型/预测工件、失败类别 |
| compare_experiments | 两个实验ID、固定协议ID | 成对分项比较和程序判定 |
| evaluate_ensembles | 同协议候选预测ID | 组合分数；无需重训 |
| finish_search | 候选ID或无改进原因 | 只选方案，不隐式部署 |

参数列表和名字是设计草案，非仓库现成 API。

修复、归一化、训练和预测之间有依赖。改变上游配置时应失效对应缓存；共享全局模型不能把每个品牌当独立权重块重训。

### 模块F：预测档案与组合感知

保存每日预测及 series/origin/date 键、模型配置、特征、数据和修复版本、随机种子、代码版本、训练预算、评估协议。

原始四个预测可以直接精确枚举15种组合。保留更多版本后组合数会增加，需要限池。Agent 看到单模型和组合贡献两种反馈，避免只优化单体排名。

对比必须在同一批 origin/series 上。缺行、重复键、horizon不一致应使评估失败；不能静默填充后仍当有效实验。

### 模块G：异常修复作为版本化实验前处理

沿用已有四模型参考序列 + factual 加权规则，不让模型口头“改一下异常值”。保留原始数据、异常标记、参考序列、权重及生成时间范围。

一次搜索中可冻结repair，便于比较。将来确需调repair时，用新数据处理版本重新评估。历史回测每个起点不能看到未来；全量数据上一次性找异常后回测，可能破坏这个条件。

阈值本轮不假定通用数字：可由更早期走步残差校准，结合异常日比例、累计偏差和业务事件；以误修风险和下游预测表现验证。真实促销、门店变化不能默认视为脏数据。

### 模块H：实验记忆与时序知识

永久知识：业务定义、模型能力、评估契约和已验证操作规则。
当前事实：本版本最好候选、剩余预算、运行中作业。
相关经验：相同模型/特征组失败案例、相似序列的有效配置、跨版本参考。
按需证据：残差表、归因和日志路径。

跨品牌可以借配置和假设，不能借别的品牌分数充当当前证据。旧数据配置可先回放检验；概念漂移后应该降低旧结论可信度。

检索不一定要向量库：按 model_id、feature_group、dataset_version、error_type 过滤的实验表已经很有用。LLM 读取摘要，必要时按 artifact_id 查细节。

## 5. 一个完整单步示例

以下为虚构流程示例，无真实企业指标。

观察：当前候选在多个开发AP的月末误差高；相关特征组已确认可见；一组高度相关的历史变量归因不稳定。

Agent 提议：
- parent：当前已评估方案；
- evidence：月末残差工件、相关性工件、归因工件；
- hypothesis：此特征组可能增加该模型的不稳定性；
- action：只在某个模型上做成组消融；
- success：按原协议看主分数与月末分项，不改变标签或切分；
- cost：请求一项训练预算。

Harness 先确认是否允许模型各自选特征。如只能共享特征，返回真实影响范围和预算，而非假装只重训一个。合法后提交作业并持久化ID。

完成后评估器生成结果，组合工具重算子集。结果若没有提升，记录反证并保留原方案；如果提升较小，按既定复核规则决定是否增加完整预算/种子。Agent 不能通过换指标、缩短测试或重命名配置让实验变成功。

## 6. Prompt / Context 的建议模板

### 固定提示负责行为

“依据工具证据提出一个可检验假设。证据不足先调用诊断。只能使用注册动作。不得改评估协议或推断未返回指标。区分观察与假设。允许实验无改善，允许正常停止。”

这段只是方向示例，不是已验证有效的最终提示。用回放案例评价提示改动，而不是仅凭阅读感觉。

### 每轮上下文负责事实

task_spec_id、data_version、evaluation_protocol_id；
incumbent摘要；
当前/最近相关实验（成功与失败）；
未决假设；
预算和运行中job；
可用工具及模型能力；
本轮相关诊断工件。

避免每轮重发三千行脚本、所有原始序列和全部日志。必需的具体事实以结构化字段保留，详表按需加载。

### 输出建议

action_type、parent_experiment_id、evidence_ids、hypothesis、config_patch、budget_request、expected_observation。
停止时返回 stop_reason 和目前最好合法候选。不要要求模型必须声称找到提升。

## 7. 验收：如何证明“时序特化”真的有效

先构造离线轨迹和模拟工具，不用每次验证都重训。

| 案例 | 合格行为 |
|---|---|
| 加入未来真实销量 | 在提交前拒绝 |
| 错误把 level-key 当可删除模型输入 | 先读角色元数据 |
| 跨AP使用未来信息拟合标准化/repair | 协议校验失败 |
| horizon不匹配或缺一个组织预测 | 不评分、不晋升 |
| 归因低但消融显著变差 | 保留列，记录失败假设 |
| 单模型变差但组合变好 | 按预定组合目标判断 |
| 只完成部分全局序列 | 不把部分结果当完整胜者 |
| 跨版本重复配置 | 区分可回放与当前已跑重复 |
| 训练成功但LLM自报更好分数 | 只信评估服务数值 |
| 连续无改善 | 预算内有限探索，允许保留基线结束 |
| 重启时GPU作业仍运行 | 查回原job，不新建重复训练 |
| 新品牌缺少已用future列 | 拒绝不兼容配置或提出合法替代 |

随后在相同训练资源预算下比较：现有人工作业/固定基线、简单自动搜索、通用Agent、加入时序特化的Agent。观察有效实验率、泄漏拦截、完整预测率、最终留出表现、最差组织退化、资源和人工介入。这里提出的是验证设计，尚无本项目实验结果。
